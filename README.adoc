= The Elixir Cross Referencer
:doctype: book
:pp: {plus}{plus}
:toc:
:toc-placement!:

Elixir is a source code cross-referencer inspired by
https://en.wikipedia.org/wiki/LXR_Cross_Referencer[LXR]. It's written
in Python and its main purpose is to index every release of a C or C{pp}
project (like the Linux kernel) while keeping a minimal footprint.

It uses Git as a source-code file store and DuckDB for cross-reference
data. Internally, it indexes Git _blobs_ rather than trees of files to avoid
duplicating work and data. It has a straightforward data structure
(reminiscent of older LXR releases) to keep queries simple and fast.

You can see it in action on https://elixir.bootlin.com/

link:CHANGELOG.adoc[Changelog]

= Requirements

* Git (to clone this repository)
* Docker (or a compatible container runtime)

All other dependencies (Python 3 and its libraries, DuckDB,
Universal Ctags, Apache) are bundled in the Docker image.

Running the test suite on a host has additional requirements, see the
_Automated testing_ section.

= Installation and deployment (Docker)

The container image is used for both serving the web pages and indexing:
the `index` command, available inside the container, clones (or updates)
the git repositories and builds the databases.

== Data directory layout

Elixir keeps all its data (git repositories and databases) under a single
root directory. In the container this is `/srv/elixir-data`, with one
sub-directory per project:

----
/srv/elixir-data/
  <project 1>/
    data/
    repo/
  <project 2>/
    data/
    repo/
----

`data` holds the cross-reference database (`data.duckdb`, see
<<_the_data_layer>>) and `repo` the bare git repository of the project. The
`index` command creates and fills these directories, so you normally never
manipulate them yourself.

== Build the Docker image

Dockerfiles are provided in the `docker/` directory.
To build the image, run the following commands:

 # git clone https://github.com/bootlin/elixir.git ./elixir
 # docker build -t elixir --build-arg ELIXIR_VERSION=`git rev-parse --short HEAD` -f ./elixir/docker/Dockerfile ./elixir

The ELIXIR_VERSION build argument is optional. Since .git directory is not copied into Docker image by default,
the option is used to pass a version string to Elixir.

== Run the container

 # mkdir ./elixir-data
 # docker run -v ./elixir-data/:/srv/elixir-data -d --name elixir-container -p 80:80 elixir

This starts Apache inside the container and serves Elixir on port 80
of the host.

== Index a project

The Docker image does not contain any repositories.
To index a repository, you can use the `index` script.
For example, to add the https://musl.libc.org/[musl] repository, run:

 # docker exec -it elixir-container index /srv/elixir-data musl

Or, to run indexing in a separate container:

 # docker run -v ./elixir-data/:/srv/elixir-data \
    --entrypoint index elixir /srv/elixir-data musl

You can also use `index /srv/elixir-data --all` to start indexing all officially supported repositories.

The `index` command fetches the project's remotes (creating the bare
repository on first run) and then runs `update.py` to build the databases.
Run it again at any time to index newly released versions.

You can set `$ELIXIR_THREADS` if you want to change the number of threads used by
update.py for indexing (by default the number of CPUs on your system).

`update.py` indexes the new tags one at a time, the oldest first, in one
transaction per tag, and `utils/index` runs it after each fetch.

____
Generating the full database can take a long time: it takes about 15 hours on a Xeon E3-1245 v5 to index 1800 tags in the Linux kernel. Progress is committed after each tag, so you can interrupt indexing and run it again later to continue where it stopped. You can even create a new Git repository and just create one tag instead of using the official kernel repository which is very large.
____

After indexing is done, Elixir should be available under the following URL on your host:
http://localhost/musl/latest/source

== Verifying the installation

`utils.query` needs to know which project to work on,
through the `LXR_REPO_DIR` and `LXR_DATA_DIR` environment variables:

 # docker exec \
    -e LXR_REPO_DIR=/srv/elixir-data/musl/repo \
    -e LXR_DATA_DIR=/srv/elixir-data/musl/data \
    elixir-container python3 -m utils.query ident latest malloc C

NOTE: `latest` can be replaced with any other tag, and `malloc` with any
other identifier.

You can also check the web pages and the REST API (see below) served by
the container.

== Automatic repository updates

The Docker image does not automatically update repositories by itself.
You can, for example, start `index /srv/elixir-data --all` in the container (or in a separate container, with Elixir data volume/directory mounted)
from cron on the host to periodically update repositories and index new
releases.

== Using Docker image as a development server

You can easily use the Docker image as a development server by following the steps above, but mounting Elixir source directory from the host
into `/usr/local/elixir/` in the container when running `docker run elixir`.

Changes in the code made on the host should be automatically reflected in the container.
You can use `apache2ctl` to restart Apache.
Error logs are available in `/var/log/apache2/error.log` within the container.

== Updating a live deployment without downtime

DuckDB's lock model allows exactly one read-write opener (the indexer)
or any number of read-only openers (the web/API workers), never both
on the same file at the same time. Serving and indexing therefore run
on separate copies, swapped by operations — Elixir itself has no
data-dir rotation logic:

. The web/API containers serve from a copy of `data.duckdb` they only
open read-only.
. A separate indexing container (or a one-off `docker run --entrypoint
index ...`) updates its own copy of the project's `data/` directory;
`update.py` leaves one clean, checkpointed `data.duckdb` (no WAL, no
scratch files) when it finishes.
. Rotation is an ops concern: copy the fresh file over the served copy
and restart/reload the serving containers. A half-copied file is
never observed because readers open it once at request time.

== The data layer

All cross-reference data of a project is one DuckDB database,
`<project>/data/data.duckdb` (`elixir/data_duckdb.py` is the access
layer):

* `blobs`, `versions` and `idents` are small dimension tables with a
PRIMARY KEY; their integer ids are dense counters assigned by
`update.py` in deterministic walk order (no sequences). `idents`
additionally carries an ART index on `name` — the query hot path.
* `version_objects`, `defs`, `refs` and `docs` are fact tables with no
constraints and no indexes: their access path is physical clustering.
`update.py` writes them through staging twins (`<table>_stage`, hidden
from readers by the `<table>_all` views) and rebuilds each main table
ordered by its cluster key (leading `identid`) at the end of the run,
so ident lookups scan one contiguous range.

Each indexed tag commits as one transaction. A killed run loses at
most the tag in flight and resumes at the last committed tag when run
again; there is no refusal or lock-out state after a crash.

Determinism is a property, and it is checked: the logical content of
a database is a deterministic function of the input walk, so two
fresh indexes of the same repository hash identically under
`data_duckdb.canonical_dump()` (a byte-stable dump of every table in
key order). `update.py` verifies `check_invariants()` (dense ids,
referential integrity, refs only for defined idents, the per-ident
definition-family bitmasks) after every run and fails loudly instead
of publishing a broken database.

[WARNING]
====
The DuckDB file format is not stable across releases: a
`data.duckdb` written by one version of DuckDB may not open under
another. Keep `duckdb` and `pyarrow` pinned exactly (as
`requirements.txt` does, in sync with the Docker image) and expect a
full re-index when upgrading them.
====

= REST API usage

Once the container is running, you can test the API usage:

== ident query

Send a get request to `/api/ident/<Project>/<Ident>?version=<version>&family=<family>`.
For example:

 curl http://127.0.0.1/api/ident/barebox/cdev?version=latest&family=C

The response body is of the following structure:

----
{
    "definitions":
        [{"path": "commands/loadb.c", "line": 71, "type": "variable"}, ...],
    "references":
        [{"path": "arch/arm/boards/cm-fx6/board.c", "line": "64,64,71,72,75", "type": null}, ...]
}
----

= Maintenance and enhancements

== Using a cache to improve performance

At Bootlin, we're using the https://varnish-cache.org/[Varnish http cache]
as a front-end to reduce the load on the server running the Elixir code.

 | Http client | --------> | Varnish cache | --------> | Elixir container (Apache) |
 '-------------'           '---------------'           '---------------------------'

= Hardware requirements

Performance requirements depend mostly on the amount of traffic that you get
on your Elixir service. However, a fast server also helps for the initial
indexing of the projects.

SSD storage is strongly recommended because of the frequent access to
git repositories.

At Bootlin, here are a few details about the server we're using:

* As of July 2019, our Elixir service consumes 17 GB of data (supporting all projects),
or for the Linux kernel alone (version 5.2 being the latest), 12 GB for indexing data,
and 2 GB for the git repository.
* We're using an LXD instance with 8 GB of RAM on a cloud server with 8 CPU cores
running at 3.1 GHz.

= Automated testing

Elixir includes a test suite in `t/`.

== In a Docker container

The test suite and all its dependencies are part of the Docker image, so you
can run it without installing anything else on the host (assuming the image
was built as shown earlier):

 # docker run --rm --entrypoint pytest elixir t/

== On the host

Running the suite on a host requires: Git, Python >= 3.8 with the
packages listed in `requirements.txt`, and Universal Ctags.
From the top-level Elixir directory, run:

 python3 -m pytest t/

The test suite uses code extracted from Linux v5.4 and Linux v7.3-rc2 in
`t/tree`.  The v7.3-rc2 files (the `omap2420-n8x0*` devicetrees, the
`i2c-cbus-gpio`, `retu-mfd` and `fixed` drivers, and the DT binding
documents for them) form a coherent set: the `i2c-cbus-gpio`, `nokia,retu`
and `regulator-fixed` compatible strings appear in all three roles —
defined in C drivers, used in devicetrees, documented in bindings.

== Licensing of code in `t/tree`

The copied code is licensed as described in the https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/COPYING[COPYING] file included with
Linux.  The v5.4 files all carry SPDX license identifiers of `GPL-2.0+` or
`GPL-2.0-or-later`.  Per https://www.gnu.org/licenses/gpl-faq.en.html#AllCompatibility[GNU's compatibility table], GPL 2.0+ code can be used
under GPLv3 provided the combination is under GPLv3.  Moreover, https://www.gnu.org/licenses/license-list.en.html#AGPLv3.0[GNU's overview
of AGPLv3] indicates that its terms "effectively consist of the terms of GPLv3"
plus the network-use paragraph.  Therefore, the developers have a good-faith
belief that licensing these files under AGPLv3 is authorized.  (See also https://github.com/Freemius/wordpress-sdk/issues/166#issuecomment-310561976[this
issue comment] for another example of a similar situation.)

The v7.3-rc2 files are unmodified test data, kept verbatim with their
upstream headers: the devicetrees and the bindings documents are
`GPL-2.0-only`, `fixed.c` is `GPL-2.0-or-later`, and `i2c-cbus-gpio.c` and
